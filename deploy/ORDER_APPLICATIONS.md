# Contact-request checkout

New checkout submissions create `Order.kind=APPLICATION`, status `NEW`, line-item/contact snapshots, a shipment and an audit entry. They never create `Payment` or `FiscalReceipt`. When Ozon is selected, the verified quote and consent produce an immutable `OzonDeliveryJob` atomically with the order. The worker creates the carrier order without payment, using the same request and idempotency key on retry. Any obsolete payment form value is ignored. Old browser payment actions are disabled.

Incoming requests appear at `/admin/orders/` and through **Заявки покупателей** in the account menu. Contact the buyer manually. Supported application statuses: NEW, APPROVED, IN_PROGRESS, PACKED, SHIPPED, DELIVERED, CANCELED. Internal notes and tracking are editable. Ozon creation happens when submitting the application, not when changing its status. Readiness approval remains manual after contacting the buyer; no automatic fiscalization or bank payment occurs.

DELIVERED requires explicit staff confirmation that the purchase happened and the buyer received the goods. `purchaseConfirmedAt` plus the account-owned delivered line item permits a verified-purchase review. Merely submitting an application never does. Reopening/canceling clears this attestation.

Deletion requires `orders.write` and matching order-number confirmation. It sets `deletedAt` and `OzonDeliveryJob.cancelRequestedAt` atomically with audit. Deleted orders disappear from active admin/customer lists; staff can inspect their history under **Удалённые**. The worker cancels all postings, skips confirmed canceled postings, and only marks CANCELED after remote status confirmation. Unsent jobs are canceled locally. In-flight creation retains its lease, saves the response, then cancellation proceeds. Ambiguous/partial creates are reconciled with the original immutable key/body before cancellation; cancellation intent survives failures/restarts. Delivered shipments cannot be canceled: an explicit warning is retained in the archive, never a false success. Existing bank/fiscal/carrier records remain; deletion does not refund money. Archived applications cannot be edited or accessed through customer detail/success pages. Customer documents from historical purchases remain accessible to their owner.

Legacy payment integrations are tucked into an archive section in administrator settings; old obligations still reconcile. No new application uses those settings, even if the old integration remains enabled. Fresh carrier creation never claims an archived/cancel-requested order. Cancellation reconciliation may replay an already attempted create only with its original key to discover the remote postings, then cancel them.

Email confirmation retains the existing opt-in processor configuration; no new external notifier is configured. Administrator delivery of requests is through the dashboard/list, not a promise of email/SMS notification.

Additive migrations: `20261006020000_order_applications`, `20261006030000_application_ozon_delivery`. Prior order kind is ORDER; historical payment/shipping data is not rewritten. Tests cover isolated local HTTP workflows, consent, no financial records, Ozon outbox and idempotent creation/cancellation, in-flight deletion, partial/ambiguous responses, provider failures, status confirmation, review eligibility, archival and preserved fiscal receipts.

For applications received during the preference-only release, an administrator can use **Создать отправление Ozon**. The repair requires an active application, selected point, persisted non-revoked Ozon consent and real packaging; it recalculates availability before enqueueing. Existing jobs, tracking, shipped/completed/canceled/deleted applications cannot be duplicated by this repair.
