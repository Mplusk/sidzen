# Интернет-эквайринг Точка

Новые онлайн-платежи магазина создаются только в Точке. Оплата по счёту сохранена.
Старые платёжные записи и зашифрованные ключи ЮKassa не удаляются: они нужны для сверки ранее созданных оплат. Старые формы checkout с `payment=yookassa` отклоняются.

## Подключение

ЛК администратора → **Доставка и оплата** → **Точка · интернет-эквайринг** (`/account/integrations/`).

1. Подключите интернет-эквайринг для сайта в банке. Торговая точка должна иметь `status=REG`, `isActive=true` и нужные способы оплаты.
2. Выпустите JWT-ключ в разделе «Интеграции и API» Точки с правами `ReadCustomerData`, `ReadAcquiringData`, `MakeAcquiringOperation`. Вставьте ключ без `Bearer`. Поле скрыто; секрет сохраняется с AES-256-GCM, не выдаётся HTML и не попадает в аудит.
3. Введите `customerCode` (9 символов, компания `Business` из Get Customers List) и `merchantId` (15 цифр из Get Retailers).
4. Выберите карту / СБП и настройки кассы. Для чеков Точки касса должна быть подключена в банке; укажите НДС и систему налогообложения. Для собственной кассы подтвердите самостоятельную выдачу чеков. Не выбирайте налоговые параметры произвольно.
5. Нажмите «Проверить и сохранить», затем включите приём онлайн-платежей и сохраните. Проверка выполняет только GET: не создаёт платежей, не списывает деньги и не передаёт контакты покупателя. Доступ на создание проверяется только при реальном запросе создания платежа; факт успешной проверки чтения не заменяет настройку `MakeAcquiringOperation`.

Пустое поле JWT сохраняет прежний ключ. Выключенные незавершённые настройки можно сохранить без запроса в банк. Без проверки и настроенной фискализации онлайн-оплата не показывается покупателю. Код компании / торговую точку нельзя заменить при незавершённых платежах; ключ той же компании можно обновить.

## Подтверждение оплаты

- Создание: `POST /uapi/acquiring/v1.0/payments` либо `payments_with_receipt`, одноэтапная оплата, карты не сохраняются. Суммы в рублях; ссылка действует 24 часа.
- Для кассы передаём email и товары (`paymentObject=goods`, цена за единицу, количество, `full_prepayment`). Бесплатная доставка не добавляется к сумме чека. Закрывающие чеки при передаче товара, возвраты и зачёт предоплаты оформляет продавец через свою кассу / банк; автоматизации этих операций в магазине нет.
- Только свежий авторизованный GET с `status=APPROVED` и совпадением суммы, компании, торговой точки, `operationId` и уникального `paymentLinkId` переводит оплату в `PAID`. Удержание `AUTHORIZED`, частичная оплата и возврат не считаются новой оплатой. Параметры возвратной ссылки не подтверждают оплату.
- Рабочий процесс сверяет до 10 незавершённых оплат за проход, примерно раз в минуту; повторная проверка выполняется и на защищённой странице заказа. Отключение новых платежей не выключает сверку существующих.
- До POST в базе фиксируется попытка и привязка к торговой точке. Если ответ потерян, повторный клик ищет существующую ссылку по `paymentLinkId`, не создавая вторую. Если ссылка не найдена или найдены дубли, нужна ручная сверка в банке. Заказ с незавершённой ссылкой / неоднозначной попыткой нельзя удалить до сверки.

## Вебхук (не обязателен для фоновой сверки)

Создайте подписку методом Create Webhook для своего `client_id`: `webhooksList=["acquiringInternetPayment"]`, `url=https://3dprinta.shop/api/payments/tochka/`. Нужно право `ManageWebhookData`. Не заменяйте существующие подписки других сервисов без проверки — на приложение может быть один вебхук.

Обработчик принимает текстовую строку JWT, ограничивает размер 32 КиБ, проверяет RS256 официальным ключом `https://enter.tochka.com/doc/openapi/static/keys/public`, затем получает операцию из банка повторно. Неподписанные события не принимаются; события неизвестных платежей не запускают запросы в банк. Ошибка сверки возвращает 503 для повторной отправки. Подтверждение регистрации / подписанные тестовые события получают 200 без изменения заказа.

## Проверки и ограничения

Unit-тесты проверяют подпись / подделку уведомлений, подмену суммы и торговой точки, статусы, шифрование, фискальные поля и повторные запросы. Синтетические проверки PostgreSQL проверяют конкурентное создание, восстановление после потери ответа и однократную смену статуса; HTTP-проверки — права, скрытие ключа и запрет включения без настроек. Песочница банка даёт фиксированные примеры: перейти по ссылке и реально оплатить в ней нельзя. Полный сценарий списания и выдачи чека требует ваших рабочих ключей и отдельной согласованной проверки.
