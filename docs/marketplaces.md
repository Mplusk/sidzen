# Импорт каталога Ozon / Wildberries

Администратор: **Личный кабинет → Маркетплейсы** (`/account/marketplaces/`).
Нужны права `settings.write`, `products.write` и `products.publish` (или роль superadmin): синхронизация может обновлять уже опубликованные товары.

1. Введите Client ID + API Key Ozon либо токен WB с правами чтения «Контент» и «Цены и скидки».
2. Нажмите «Проверить и сохранить». Пустое поле ключа сохраняет существующий ключ. Ключи шифруются AES-256-GCM с отдельным назначением, не возвращаются браузеру и не попадают в аудит.
3. Выберите основной источник и категорию новых товаров.
4. Запустите синхронизацию нужного маркетплейса. Запуск ручной, товары на маркетплейсе не изменяются. Страницу можно закрыть.
5. Проверьте журнал и спорные карточки. Новые товары сохраняются черновиками с нулевым остатком; перед публикацией задайте доступность, варианты и категорию.

## Сопоставление и приоритеты

- Сначала стабильная привязка `(маркетплейс, кабинет продавца, ID карточки)`, затем артикул продавца и штрихкоды. Для артикула применяется Unicode NFKC, нормализация пробелов и регистра; пунктуация сохраняется. Для штрихкодов сохраняются ведущие нули.
- Таблица уникальных идентификаторов хранит прежние и альтернативные артикулы. Артикул сайта, URL и публикация остаются локальными.
- Противоречивые идентификаторы, одинаковые названия без общего идентификатора, совпадение с вариантом, вторая карточка одного маркетплейса для того же товара требуют проверки. По одному названию товары не объединяются. Если идентификаторы и названия полностью отличаются, система не может определить физическое совпадение: перед импортом задайте общий артикул/штрихкод либо заранее сопоставьте карточки через существующие идентификаторы.
- Название, описание, характеристики, фотографии, цена продавца и старая цена выбираются из сохранённых снимков по фиксированному основному источнику. Отсутствующие необязательные данные могут поступить из другого источника. Последовательность Ozon → WB и WB → Ozon даёт одинаковые управляемые данные после импорта обоих источников.
- Из `/v4/product/info/attributes` Ozon загружаются **вес с упаковкой** (`weight`, `weight_unit`) и **габариты упаковки** (`depth`, `width`, `height`, `dimension_unit`). Единицы переводятся в граммы/миллиметры, дробные размеры посылки округляются вверх. Импортируется только полный, положительный комплект в допустимых пределах; неизвестные единицы и неполная упаковка не заменяют ранее заполненные поля. Вес и габариты самого изделия берутся отдельно из однозначных именованных характеристик с единицами. Упаковка не подставляется вместо самого изделия. На странице товара измерения показаны раздельно.
- В режиме «Данные сайта» имя, цена и заполненные измерения не заменяются. Импорт может заполнить ранее пустые измерения самого изделия; комплект упаковки — только если все четыре поля пустые. Частично вручную заполненная упаковка не смешивается с API. В автоматическом режиме новые корректные измерения заменяют прежние по основному источнику. Каждая упаковка выбирается из одного источника целиком.
- Не синхронизируются остатки FBO/FBS, категории маркетплейса, производственные опции, варианты, SEO, себестоимость, публикация и пользовательские заказы. Валюта автоматического импорта — RUB; специальные скидки покупателя/клуба не используются. Цены WB разных размеров не сводятся к одной автоматически: ручное сопоставление включает режим «Данные сайта».
- Изменение управляемых полей через редактор товара включает режим «Данные сайта». Синхронизация сохраняет снимки и привязки, но не заменяет эти поля. Вновь включить импорт можно здесь же; он применится при следующем запуске.
- Смена кабинета продавца при существующих привязках блокируется. Ротация ключа того же кабинета разрешена.
- Исчезновение карточки из API не удаляет товар сайта. Это защищает заказы и данные от временной недоступности API и архивирования на маркетплейсе.

## Выполнение

`marketplace-worker` в Docker использует очередь PostgreSQL. Запуски сериализуются; транзакционная блокировка, уникальные ограничения, аренда задания с heartbeat и контроль страницы предотвращают параллельное создание и повторный учёт карточек при восстановлении после падения. При ошибке журнал показывает обработанную часть; повторный запуск безопасен. Автоматической периодической синхронизации нет.

На время активного импорта создание/сохранение товаров и изменение правил блокируются, чтобы исключить конкурирующую правку. Остановка прекращает последующие изменения, уже обработанные карточки сохраняются.

Ozon: `/v3/product/list`, `/v3/product/info/list`, `/v5/product/info/prices`, `/v4/product/info/attributes`. Описание — атрибут 4191. WB: `/content/v2/get/cards/list` с `withPhoto: -1`; цены загружаются общим списком GET `/api/v2/list/goods/filter` с пагинацией, без платного пакетного POST по артикулам. API проверяется по схемам; неожиданный формат прекращает импорт, а не молча пропускает страницу.

Названия характеристик Ozon запрашиваются через `/v1/description-category/attribute` по паре категории и типа товара, со справочником на время одного запуска. ID характеристик не отображаются покупателю; название/код продавца, настройки объединения, маркировки и таможенные коды не импортируются в витринную таблицу. «Нет бренда» не добавляет пустую характеристику бренда. Неизвестные старые ID скрываются на витрине, но сохраняются в базе до достоверного сопоставления.

Исправление ранее загруженных характеристик: `pnpm exec tsx scripts/repair-ozon-specifications.ts` — предварительный просмотр; `--apply` — применение с аудитом и проверкой конкурентных изменений. Меняются только старые ключи `Ozon · ID` в снимке и карточке; ручные именованные поля, цены, наличие, публикация и режим «Данные сайта» сохраняются. Перед применением сделайте резервную копию.

Фото копируются в постоянный том сайта. Только HTTPS на разрешённых CDN провайдера; редиректы запрещены, ключи не передаются, ограничение 10 МБ/фото, проверка сигнатуры JPEG/PNG/WebP/AVIF. Имена файлов зависят от SHA-256 содержимого. Файлы, используемые сохранёнными снимками, не удаляются редактором.

Вне Docker: `pnpm marketplace:worker`, те же `DATABASE_URL`, `AUTH_SECRET`, `INTEGRATION_ENCRYPTION_KEY`, что у приложения; `MARKETPLACE_APP_URL=http://localhost:3101` для локальной проверки. После обработки worker вызывает защищённую внутреннюю инвалидацию каталога; при временной недоступности приложения остаётся стандартный TTL каталога.

## Проверки

`pnpm test` проверяет адаптеры с фикстурами, порядок приоритетов, URL и секреты. `DATABASE_URL=.../shop_qa AUTH_SECRET=... pnpm exec tsx scripts/smoke-marketplaces.ts` проверяет транзакции и очередь на одноразовой локальной базе и mock HTTP, без реальных ключей маркетплейсов. Этот тест также выполняется в CI с отдельным PostgreSQL. Настоящий кабинет и фактический ассортимент можно проверить только после ввода действующих ключей; фикстуры не заменяют такую проверку.
